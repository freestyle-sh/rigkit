This guide creates a minimal Rigkit project, prepares it once, and creates one
workspace.

## Install

```sh
curl -fsSL https://www.rigkit.dev/install | sh
```

Open a new terminal, then verify the CLI:

```sh
rig version
```

## Initialize a project

```sh
mkdir website
cd website
rig init
```

`rig init` writes `rigkit/index.ts`, adds `@rigkit/sdk`,
`@rigkit/provider-freestyle`, and `@rigkit/provider-cmux` to `package.json`
(creating it if needed), then asks which package manager should install them.
Pass `--package-manager pnpm` to skip the question or `--no-install` to only
write files. It does not write `.env` or ignore rules, so add `.rigkit/` to
`.gitignore` yourself.

<Note>
Agents, CI, and other non-interactive callers can parse JSON:

```sh
rig --json init
```

JSON mode skips dependency installation. Use `--json` on later commands, and
use `--yes` when removing workspaces.

</Note>

The generated config uses Freestyle browser login by default:

```ts
const freestyleProvider = freestyle.provider();
```

If you want API-key auth, change that line to:

```ts
import { env } from "@rigkit/sdk";

const freestyleProvider = freestyle.provider({
  apiKey: env.secret("FREESTYLE_API_KEY"),
});
```

## What was generated

The starter config exports one workflow named `dev` with three tasks. It
prepares a Freestyle VM (the base image ships Node.js, bun, and git) and
installs GitHub CLI, opens a browser-backed `gh auth login` terminal when the
VM is not yet authenticated, and clones `octocat/Hello-World`. Each task
snapshots the VM and passes the snapshot id forward.
Every command, terminal, and editor session in it runs as `root`; see
[Linux user](/providers/freestyle#linux-user) for why that is stated
explicitly.

It also defines workspace lifecycle hooks plus `ssh`, `open-cmux`, and
`open-vscode` operations. The workflow context stores the snapshot id and
cloned repository path; each workspace stores its VM id.

## Plan and apply

```sh
rig plan
rig apply
rig plan
```

The first plan shows the three tasks as pending. `rig apply` runs them and
stores each task's output in `.rigkit/state.sqlite`. The second plan should
show every task as cached.

Cached output is reused until something it depends on changes: task code,
provider config in scope for the task, upstream task output, or the output
schema. It is also dropped when a `cacheTTL` expires, a provider reports a
cached artifact as gone, or you invalidate it by hand.

## Create a workspace

```sh
rig create dev
rig ls
```

`rig create` always runs `apply` first, which is a no-op when everything is
cached, then calls `workspace.create`. Remove the workspace when you are done:

```sh
rig rm dev
```

## Run an operation

```sh
rig apply
rig create dev
rig run dev ssh
rig run dev open-cmux
rig run dev open-vscode
```
